# Changelog

All notable changes, bug fixes, and feature additions to `ltxq` are documented here.

## [Unreleased] - 2026-09-06

### Feature: visual continuity for audio batches (`add-batch --chain`) + batch-scoped chain dispatch gate

- **`ltxq.py`**: `add-batch` gained `--chain` — segments 2..N are created with `chain=image` so `resolve_chain` attaches the previous segment's last frame as `--image` at launch time (segment 1 stays unchained; the `--image` slot is the correct continuation target — a lone `--first-frame` is invalid, it only pairs with `--last-frame`). To make the batch-scope chain deterministic under parallel hosts, `dispatch()` now defers any queued job that has both `chain` and `batch` while another job of the same batch is active (uploading/running/collecting/suspect/cancelling): the batch self-serializes and the "most recent finished job in batch" chain source is always the true predecessor. Unbatched chain jobs and unchained batch jobs are unaffected; unrelated jobs still dispatch freely around a deferred batch. Tested end-to-end on a scratch db with a fake local host and a real 1-second test video as the finished predecessor: deferral while active, frame extraction (`chain_<pred>_f24.png` → `--image` in runner.sh) after completion, and continued deferral of the next segment.
- **`server.py`**: `/api/add-batch` accepts a `chain` field (any non-empty value enables it); **`static/index.html`**: "Visual continuity" checkbox on the audio batch form with a note that it serializes the batch.
- **`docs/features.md`**: CLI bullet, Web-UI bullet, and the known-issues chain entry updated (batch-scoped chain is now race-free; unbatched chain keeps the global racy scope); **`docs/api.md`**: chain field documented (folded into unreleased 1.6); **`docs/expansion-of-this-idea.md`**: Idea 1's visual-continuity open question marked resolved.

### Feature: audio-batch form in the dashboard (`/api/add-batch`, API 1.6)

- **`server.py`**: new `POST /api/add-batch` endpoint (API 1.6, additive) — queues one job per `.wav` via `ltxq.cmd_add_batch`, routed through an argparse `Namespace` exactly like `/api/add` does for `cmd_add`. Two segment sources: folder files uploaded from the browser (staged flat into `jobs/_tmp/batchseg_*` for the request, removed afterwards) or a server-side directory path typed into the form. Config falls back to the last completed job's config when no per-model template exists (same rule as `/api/add`); a refused validation returns 400 with the per-item error list and queues nothing. Each created jid is published to the SSE bus. Verified both modes through the Flask test client against a scratch database (no live-engine dispatch risk) and over real HTTP on a scratch server on port 8899.
- **`static/index.html`**: new "Audio batch" card between the add form and History — model/host/ext selects (options mirrored from the main form's `loadModels`), folder picker (`webkitdirectory`) and folder drag-drop (entries-API traversal), server-side path field, shared fallback prompt, non-8n+1 policy selector, seed / batch label / config-JSON overlay. Shows a `N files selected (k .wav)` label on the dropzone; validation errors surface through the flash message.
- **`docs/api.md`**: endpoint section + version 1.6; **`docs/features.md`**: Web-UI bullet; **`docs/expansion-of-this-idea.md`**: Idea 1 status notes the web form as shipped.

### Feature: `add-batch` — audio-segment batch composer (Idea 1)

- **`ltxq.py`**: new `add-batch <dir>` subcommand — queues one job per `.wav` segment in a directory. Frame counts come from the cutting helper's manifest when present (per-file lines taken verbatim, cross-checked against the wav list, the `Total Segments` header and the Raw Frame Counts block, plus a manifest-fps vs template-fps guard); without a manifest each wav is ffprobed and its duration snapped onto the 8n+1 grid at the template fps. Non-8n+1 lengths default to round-up with an ffmpeg silence pad (`--on-non-grid round-down` trims instead, `refuse` aborts the batch) — the spoken content is never cut. Prompts come from same-basename `.txt` sidecars next to the wavs, falling back to a shared `--prompt-file`; a segment with neither (or an empty prompt) is a validation error. Job names are the segment basenames, the `batch` label defaults to the manifest's Original File stem (else the directory name), `--seed` is shared across the batch (absent → engine-random per segment), and `numFrames` is written into each job's `config.json` (not the `--frames` override) so regen, metadata duration, and the UI stay consistent. The whole batch is validated up front and refused with a per-item error list before anything is queued.
- **`ltxq.py`** (refactor): `_cmd_add` split into `_load_cfg()` (template resolution + shared config warnings) and `create_job()` (job dir, runner.sh, db insert — the shared tail of every creation path, ready for the web API and future batch modes); `add` behavior is unchanged (default job name derivation moved into `create_job`).
- **`docs/features.md`**: CLI list + `add-batch` bullet; **`docs/expansion-of-this-idea.md`**: Idea 1 marked **Done (v1)** and its spec updated to the round-up default; web bulk mode and reassembly remain open (Idea 4).
- Tested end-to-end with synthetic segment dirs: manifest batch (grid + non-grid + sidecar/fallback prompts), no-manifest batch (ffprobe snap, shared seed), round-up pad vs round-down trim (fitted wav durations verified by ffprobe), and the refusal paths (non-grid refuse, missing prompts, fps mismatch, under-9-frame segment, manifest count/order/fps cross-checks, ambiguous multiple manifests). All test jobs removed afterwards.

### Feature: merge tray — merge finished job videos locally with ffmpeg (API 1.5)

- **`ltxq.py`**: `merge_items` table added to the schema (ordered tray entries; existing dbs pick it up on next engine start via `CREATE TABLE IF NOT EXISTS`). No CLI change.
- **`server.py`**: new merge-tray section — one implicit ordered playlist of finished jobs' collected videos with `POST /api/merge/add|remove|move|clear|run` and `GET /api/merge/file/<name>` (API 1.5, additive; `merge` + `merge_run` fields also embedded in `/api/state` and published as a `merge` SSE event). `/api/merge/run` ffprobe-validates every clip (codec/width/height/fps must match — v1 refuses mismatches instead of re-encoding) and concatenates with stream-copy (`-f concat -c copy -movflags +faststart`) into `movies_dir/merges/<name>.<ext>` (auto-suffixed, never overwrites), parsing ffmpeg `-progress` output for a live percent. The merge is a local subprocess in a background thread — it never touches the engine loop, `engine.lock`, or remote hosts, so it's safe to run while the queue renders. Includes a scratch-server live test pass (add/move/remove/clear, real two-clip merge with duration verification, download endpoint, path-traversal guard).
- **`static/index.html`**: "Merge tray" card under History — ordered rows with ↑/↓/✕ per entry plus Clear; ➕ button on done history rows appends a job's video; "Merge…" prompts for an output name and shows a progress bar, then a download link for the finished file (missing artifacts gray out the button with a "video missing" badge).

### Feature: dispatch-time `--fflf-preflight` for first+last-frame jobs

- **`ltxq.py`**: oneshot `launch()` now runs one extra `generate --fflf-preflight` on the host when the job carries both `--first-frame` and `--last-frame` assets — after `resolve_chain`, so chain-attached frames (which don't exist until the job's turn in the queue) are validated too. The shared argument string was factored out of `make_runner` into `gen_args()` so the probe and the real render stay in sync. A failing check (engine exits nonzero) fails the job with the engine's message instead of burning a render; full output lands in the job dir's `preflight.txt`, a summary goes to the job note. Transport errors skip the check and render anyway (5-min timeout guards the engine loop). First-frame-only, middle-only, and serve-backend jobs are not preflighted (the engine flag validates the FFLF pair). The host CLI/models-dir existence checks were split into their own ssh call ahead of the preflight so their friendly error notes win over a raw preflight failure.

### Feature: `--video-format` as a hosts.yaml preset (default hevc, per-host override)

- **`ltxq.py`**: new global `video_format` key (default `hevc`) with per-host override, resolved by `video_format_of()` and appended as `--video-format <v>` in both backends — `make_runner` (oneshot, at dispatch time where the host row is known, like `models_dir`) and `serve_args` (serve). Only emitted for video outputs (`mov`/`mp4`); an explicit empty string on a host omits the flag entirely; `hosts` table gained a `video_format` column (migration) synced from yaml via `COALESCE` (absent key keeps the stored value). ProRes + `.mp4` conflict is left to the engine's own error, documented in environment.md.

### Security
- **Web dashboard hardening (`server.py`, `ltxq.py`)**: Closed an arbitrary-file-read/delete and an arbitrary-file-write reachable via the localhost API. (1) Job-id path traversal: `/api/asset`, `/api/stage_from`, `/api/delete`, `/api/view`, `/api/job`, `/api/cancel`, `/api/regen`, `/api/extract` only sanitized the trailing `name` component, so a crafted id like `%2e%2e` walked out of `jobs/` — verified `GET /api/asset/%2e%2e/hosts.yaml` returned the config file, and `/api/delete` could `rmtree` arbitrary directories. All eight endpoints now require the 10-hex job-id format. (2) Upload filename traversal: multipart filenames (curl sends `../` verbatim) were joined onto `jobs/_tmp/` unmodified, letting a crafted name write outside the staging dir; all three save sites now strip to the basename. ### Fixed
- **No way to clear a selected media file (`static/index.html`)**: Each media slot on the new-job form (image, audio, input video, first/middle/last frame) now shows a ✕ button while a file is chosen; clicking it clears that input. - **File-descriptor exhaustion after hours of idling (`ltxq.py`, `server.py`)**: Every `db()` call dropped its SQLite connection without `close()`; in request/engine threads (Python 3.14) those connections are only reclaimed at the next GC pass, so with the dashboard polling `/api/state` every 2 s the process leaked its `ltxq.db`/`ltxq.db-wal` file descriptors (~2 per request) until `OSError: [Errno 24] Too many open files` / `sqlite3.OperationalError: unable to open database file` after roughly 5–7 hours. All request handlers and the `cmd_*` entry points reachable from the ui process (`cmd_add`, `cmd_regen`, `cmd_cancel`, `cmd_models`, `cmd_serve_start`) now close their connections deterministically, the engine loop closes its long-lived connection on stop and runs `gc.collect()` in the 600 s maintenance cycle, and `is_local()` resolves `conn_type` from the in-memory `HOSTDEST` cache (extended by `load_dests()`) instead of opening a connection per call — it had been called on every `ssh()`/engine tick. Schema creation and migrations now also run once per process instead of on every `db()` call. Verified: fd count stays flat (50 → 49 over 150 requests + API round-trip, vs 52 → 280 before).
