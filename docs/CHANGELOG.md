### hosts.yaml → user config location + live reload (macOS-app-friendly)

- **Config path resolution (`ltxq.py`)**: `CONF_PATH` is no longer hard-wired to the repo root. New `_resolve_conf_path()` search order: `$LTXQ_CONF` env override → repo `hosts.yaml` (existing CLI setups unchanged) → `~/Library/Application Support/Ltxq/hosts.yaml`. When nothing exists yet, `hosts.yaml.example` is seeded into the Application Support location on first start, so a fresh install always has an editable file. Added `conf_changed()` mtime helper for the engine loops.
- **Live reload (`server.py`, `ltxq.py`)**: both engine loops (in-UI thread and `ltxq.py run`) watch `hosts.yaml` and re-read + re-sync the hosts table within one poll interval of a save; parse/validation errors keep the previous config running instead of crashing dispatch.
- **`POST /api/hosts/reload` (`server.py`, API 1.3)**: validates the on-disk `hosts.yaml` (YAML parse, alias presence, duplicate aliases) and applies it, returning the effective path and host summary; returns 400 with the error and leaves the running config untouched. Also hardened `GET /api/status` to report a broken `hosts.yaml` as `conf_error` instead of a 500.
- **macOS app (`macos/Ltxq/`)**: Settings gained a `hosts.yaml` section with Edit hosts.yaml… (opens in the default editor, creating the file from the example if needed), Reveal in Finder, and Apply Changes (calls `/api/hosts/reload`, shows per-host success or the validation error inline). Diagnostics now show the resolved config path, and `EngineManager` no longer hard-fails when repo `hosts.yaml` is absent — the engine seeds and resolves it itself. (`Settings.swift`, `SettingsView.swift`, `EngineManager.swift`)
- **Docs**: `docs/api.md` bumped to API 1.3 documenting the new endpoint and the engine's automatic reload behavior.

### Fixed
- **"View" button in history does nothing in the macOS app (`macos/Ltxq/DashboardView.swift`, `Probes.swift`)**: Clicking a history row's "View" (and asset image/audio links) was a no-op in the native app — these use `target="_blank"`, and WKWebView silently drops new-window requests unless the UI delegate implements `createWebViewWith`. Added that delegate method, handing target URLs to the default browser via `NSWorkspace.shared.open`. Also fixed pre-existing `isExecutableFile` → `isExecutableFile(atPath:)` compile errors in `Probes.swift` that broke `build.sh` since the tool-probe commit. App rebuilt clean.
- **Frame extraction fails in the macOS app (`ltxq.py`, `server.py`, `macos/Ltxq/EngineManager.swift`)**: "Extract & attach" (last/first/numbered frame → slot) always errored when the engine was launched from the app: a Finder-launched GUI app inherits a minimal `PATH` without `/opt/homebrew/bin`, so `extract_frame`'s `subprocess.run(["ffprobe"/"ffmpeg", …])` raised `FileNotFoundError`, which `/api/extract` didn't catch → 500 "Internal Server Error" (chain continuation was silently degraded too). Fixed on three layers: a new `ff_tool()` helper resolves ffmpeg/ffprobe via `shutil.which` plus common Homebrew/MacPorts fallback dirs; `/api/extract` catches `OSError` and returns a 400 JSON error message; and the app's spawned engine child now gets a `PATH` extended with `/opt/homebrew/bin:/usr/local/bin:/opt/local/bin`. Verified extraction works with an emptied `env -i` PATH, app rebuilt clean.
- **File dialog never opens in the macOS app (`macos/Ltxq/DashboardView.swift`, `static/index.html`)**: Clicking a "drop, paste, or click to browse" tile in the native app did nothing — WKWebView only opens a file chooser when its UI delegate implements `runOpenPanelWith` (browsers have this built in), and the shell had no UIDelegate. Added a `WKUIDelegate` coordinator presenting an `NSOpenPanel` (multiple-selection and Cancel passed back to the page), and made the dashboard's tile click handler explicitly `inp.click()` (with `preventDefault` so native label-forwarding doesn't double-open in regular browsers), removing the dependence on label activation of a 1px `opacity:0` hidden input. Verified `build.sh` compiles clean.

### Added
- **Startup/dispatch checks for missing `hosts.yaml` and remote CLI (`ltxq.py`, `macos/Ltxq/EngineManager.swift`)**: A missing `hosts.yaml` now aborts every `conf()` consumer (ui/run/doctor/add…) with a one-line actionable error and exit 1 instead of a raw `FileNotFoundError` traceback, and the macOS app treats it as a blocking startup failure with the `cp hosts.yaml.example hosts.yaml` hint (same screen as the python/script guards). The remote tod-cli binary is now verified on dispatch (`launch()` runs `test -x` on the host's `cli_path` before uploading/starting a job — missing binary leaves the job `queued` with an explicit note instead of a cryptic remote `exit 127`) and by `doctor` per enabled host (`[ok]/[FAIL] tod-cli present`), so a bad `cli_path` surfaces up front rather than after a failed job.
- **Startup availability checks for helper tools (`server.py`, `ltxq.py`, `macos/Ltxq/Probes.swift`, `EngineManager.swift`, `RootView.swift`)**: Follow-up to the ffmpeg PATH fix so tool absence is reported up front instead of at first use. `ToolProbe` (Swift) searches `PATH` plus the Homebrew/MacPorts bin dirs for ffmpeg/ffprobe at every app launch; missing tools surface as a dismissible warning banner over the dashboard (non-fatal — generation works, frame extraction/chain continuation don't) and a line in the engine log. `server.engine_loop` prints the same warning at engine start (covers CLI `run`/`ui`), and `ltxq.py doctor` gained `[ok]/[FAIL] ffmpeg/ffprobe` checks so `doctor` reports it as a hard failure.

- **SSE event stream `GET /api/events` (`server.py`, `ltxq.py`, `docs/api.md`)**: New additive Server-Sent Events endpoint (macOS-app plan Phase 1) pushing state changes as they happen instead of 2s polling only: a `hello` snapshot on every connect, then `job` events (the same object `/api/job/<jid>` returns) for every committed job mutation, plus `job_removed`, `host` health changes (worker liveness, queue depth, pause state — published immediately on pause/resume), `engine` start/stop, and a `refresh` event if a slow consumer's buffer overflows. Wiring: a new additive `ltxq.JOB_WATCHERS` hook fires after each committed `set_job` (no-op for the CLI), a bounded per-subscriber queue fans out without blocking publishers (no replay — clients re-bootstrap from `hello`), and the engine publishes a host event when its snapshot diff changes. `docs/api.md` gains the SSE contract and an explicit API version (1.1); decision #15 records the Mac-app architecture. Verified live: `curl -N /api/events` streams `hello` → `job` → `host` events on submit/pause, keep-alive pings while idle; `/api/state` and the web dashboard unchanged.
- **Batch groups + batch-scoped chain continuation (`ltxq.py`, `server.py`, `static/index.html`)**: Jobs may carry an optional `batch` label (new `--batch` on `add`/`regen`, "Batch" field on the web form, kept across regen) stored in a new additive `jobs.batch` column (migration). The "Continue from previous generation" feature is now batch-aware: a chained job with a batch attaches the last frame of the newest finished job **in the same batch** (`resolve_chain`), while unbatched jobs keep the previous all-jobs scope — this lets a batch compositor submit a continuation run that can't accidentally chain from an unrelated generation. Dispatch now orders same-second submissions deterministically (`ORDER BY created_at, rowid` in both dispatch sites), so batch submission order is preserved. UI shows 📦 badges on batched jobs (active cards + history) and the Load button restores the batch field. Verified via sandboxed tests: migration idempotence, rowid tiebreak, batch-scoped chain selection, `/api/add` label normalization (`fox v1` → `fox_v1`), `/api/regen` batch keep/override.
- **HTTP API contract doc (`docs/api.md`, linked from `docs/README.md`)**: Documents the localhost API as the shared client contract for the web dashboard, the future native macOS app, and external job-composition tools — state/submit/regen/staging/host endpoints, field reference (incl. `batch`, `chain` semantics, `@file@` extra-arg placeholder), conventions (CSRF guard, job-id validation, 4 GiB cap), and curl examples for batch submission. Additive-only change policy stated up front. Written ahead of macOS Phase 1 since the API now has multiple prospective clients.
- **Phase 0 native macOS app (`macos/`)**: Dock-launchable `ltxq.app` (SwiftUI + WKWebView hosting the existing dashboard; zero changes to `server.py`). An engine lifecycle manager probes `127.0.0.1:<port>` for a running ltxq server (fingerprinted via the `/api/state` shape) and attaches to it, or spawns `venv/bin/python ltxq.py ui` as a child — passing `--no-engine` when the `engine.lock` flock is held by another `run`/`ui`, and scanning a small port range past the configured one when it is occupied by a foreign service. Quitting terminates only the child the app itself spawned (user-visible Settings toggle keeps it running), verified for all three paths: attach, `--no-engine` attach, and owned spawn (no orphaned processes). Settings (repo path, port, keep-on-quit) persist in UserDefaults; hand-written Xcode 26 project uses synchronized folder groups; `macos/build.sh` builds without needing a shared scheme. No engine behavior changes.

### Security
- **Web dashboard hardening (`server.py`, `ltxq.py`)**: Closed an arbitrary-file-read/delete and an arbitrary-file-write reachable via the localhost API. (1) Job-id path traversal: `/api/asset`, `/api/stage_from`, `/api/delete`, `/api/view`, `/api/job`, `/api/cancel`, `/api/regen`, `/api/extract` only sanitized the trailing `name` component, so a crafted id like `%2e%2e` walked out of `jobs/` — verified `GET /api/asset/%2e%2e/hosts.yaml` returned the config file, and `/api/delete` could `rmtree` arbitrary directories. All eight endpoints now require the 10-hex job-id format. (2) Upload filename traversal: multipart filenames (curl sends `../` verbatim) were joined onto `jobs/_tmp/` unmodified, letting a crafted name write outside the staging dir; all three save sites now strip to the basename. (3) CSRF: the state-changing POST endpoints accepted cross-site form posts from web pages (browsers send `Origin`; several endpoints also used `get_json(force=True)`); a `before_request` guard now rejects POSTs whose `Origin` host doesn't match the request `Host` — non-browser clients send no `Origin` and are unaffected. (4) `MAX_CONTENT_LENGTH` (4 GiB) caps multipart bodies, and `model` values containing `..`/leading `/` are rejected before the `templates/<model>.json` lookup. `ltxq.py` additionally quotes the last unquoted `remote_dir`/`wdir` interpolations into remote shell strings (`launch`, `poll_job`, `poll_serve_job`, `_cmd_cancel`) and validates `--model` in `_cmd_add`. All fixes verified via the Flask test client (traversals 404, project dir intact, cross-origin 403, sanitized uploads, 413 on oversized body); takes effect on next `ui`/`run` restart.

### Fixed
- **No way to clear a selected media file (`static/index.html`)**: Each media slot on the new-job form (image, audio, input video, first/middle/last frame) now shows a ✕ button while a file is chosen; clicking it clears that input. Previously a picked file was stuck in its slot — the only way to drop it was reloading the page (re-entering prompt/config by hand) or submitting an unwanted attachment. Extracted/staged files already had per-badge ✕; keyframe rows are cleared by removing the row.

- **URL-safety of asset/staging links (`static/index.html`)**: History input thumbnails/links, staged-file previews, and the `/api/stage_from` re-attach calls now `encodeURIComponent` the filename — filenames with spaces previously relied on implicit browser encoding, and names containing `#`/`%`/`?` would silently truncate the request path. Verified against a live UI (`/api/stage_from` and `/api/stage/<name>` return the copied file for names containing spaces).

- **File-descriptor exhaustion after hours of idling (`ltxq.py`, `server.py`)**: Every `db()` call dropped its SQLite connection without `close()`; in request/engine threads (Python 3.14) those connections are only reclaimed at the next GC pass, so with the dashboard polling `/api/state` every 2 s the process leaked its `ltxq.db`/`ltxq.db-wal` file descriptors (~2 per request) until `OSError: [Errno 24] Too many open files` / `sqlite3.OperationalError: unable to open database file` after roughly 5–7 hours. All request handlers and the `cmd_*` entry points reachable from the ui process (`cmd_add`, `cmd_regen`, `cmd_cancel`, `cmd_models`, `cmd_serve_start`) now close their connections deterministically, the engine loop closes its long-lived connection on stop and runs `gc.collect()` in the 600 s maintenance cycle, and `is_local()` resolves `conn_type` from the in-memory `HOSTDEST` cache (extended by `load_dests()`) instead of opening a connection per call — it had been called on every `ssh()`/engine tick. Schema creation and migrations now also run once per process instead of on every `db()` call. Verified: fd count stays flat (50 → 49 over 150 requests + API round-trip, vs 52 → 280 before).

### Added
- **Generation chain / continuation (`ltxq.py`, `server.py`, `static/index.html`)**: New "Continue from previous generation" checkbox with a first-frame/image slot picker on the web form (CLI: `add --chain {first_frame,image}`).
